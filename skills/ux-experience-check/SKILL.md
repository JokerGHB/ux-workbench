# 体验检测（找茬工作台）

这个技能把「打开一个页面 → 判断该测什么 → 真跑一遍 → 把结论写回工作台」固化下来。
工具由找茬工作台提供：`ux_list_instances`、`ux_start_project`、`ux_run_check`、
`ux_create_instance`、`ux_save_report`、`ux_list_reports`。

## 一、先在工作台里解名字

用户说的项目名（「测一下我的官网」「crypto-visualizer 有问题」）先在工作台里找：

1. `ux_list_instances` 看已登记的项目和它们的文件夹；
2. 名字能对上就直接用，**不要先去磁盘翻文件夹**，也不要因为当前工作目录不同就断言项目不存在；
3. 对不上再考虑 `ux_create_instance`（本地文件夹给 `projectPath`，线上站点给 `url`）；
4. 连文件夹都说不清，才问用户。

网址只进历史记录、不进项目栏，所以临时测一个线上地址不必登记成项目。

## 二、要跑起来先起服务

本地项目没有现成网址时，用 `ux_start_project`，它会：

- 有 `dev` / `start` / `preview` / `serve` 脚本就用 `npm run`；
- 纯静态目录用内置静态服务，不需要装依赖；
- 只监听 `127.0.0.1`，端口从 5173 起找空闲的，已在跑的直接复用。

返回的网址就是实际托管出来的地址，**不要自己拼端口**。目录里根本没有前端页面时，
直说「没有可测的东西」，不要编一个网址。

## 三、跑检测

一律走 `ux_run_check`（`url` / `project` / `projectPath` / `instanceId` 四选一）。
引擎会自己决定怎么测，不需要你选模板或设阈值：

1. 探测主题能力：支持暗色就亮暗都测，不支持只测亮色；
2. 判断响应式：有 `@media` 断点才跑多视口；
3. 展开可交互状态：折叠面板、Tab、菜单、弹窗触发器逐个展开后重测，再恢复原状；
4. 在每个「视口 × 主题 × 状态」组合下跑适用的检测项。

七类检测项与判据：

| 检测项 | 判据 |
|---|---|
| 文字溢出 | `scrollWidth > clientWidth` 且被裁切、无 ellipsis 兜底 |
| 点击热区 | 可点元素 ≥ 44×44px |
| 暗色残留 | 暗色下大面积元素背景相对亮度 ≤ 0.55，面积 ≥ 2000px² |
| 对比度 | WCAG 对比度 ≥ 3.0 |
| 焦点可见 | 每次 Tab 都要有可见 focus ring |
| 响应延迟 | 点击到出现可见变化 ≤ 200ms |
| 动画掉帧 | 帧间隔 ≤ 34ms，掉帧率 ≤ 15% |

## 四、读懂结果

- 工具返回的是**按检测项分组、按元素合并后**的清单：一处 = 一个要修的元素，
  不是测量次数。别把「命中 32 次」说成「32 个缺陷」。
- 每种缺陷都有 `位置`（选择器或元素描述）和 `建议`。给用户的修法要落到具体
  工程手段上，不要复述判据。
- 三种结局必须分开说：
  - **有缺陷**：数字 + 最该先修的那个；
  - **测完干净**：明确说所有组合都通过了；
  - **没测成**：页面没打开就一个像素都没测，这次**没有运行记录**，不能说成「没问题」。

## 五、把结论写回工作台（必做）

`ux_run_check` 只留下测量事实，判断和修法要自己写：

```
ux_save_report({
  markdown: "# 标题\n## 结论\n…\n## 发现\n…\n## 建议修法\n…",
  summary: "一行结论",
  target: "<被测网址或文件夹>",
  runId: "<ux_run_check 返回的运行记录 id>"
})
```

写清楚四件事：测了什么（网址 + 组合数）、结论（几处、严重几处）、
最该先修的是哪个及为什么、怎么修。第二次测同一个页面时，先 `ux_list_reports`
看看上次的结论，能对比出「修了没有」。

## 六、汇报的口径

先说结论，再说最该先修的一处，最后给修法。不要贴工具返回的 JSON，
也不要只描述检测能力 —— 用户要的是「这个页面现在能不能上线」。
